# 系统压力测试报告

> 目标：验证系统在 **100 人同时使用** 场景下的表现，定位并消除瓶颈。

## 一、测试环境

| 项目 | 配置 |
|---|---|
| 操作系统 | Windows 11 |
| CPU | 12 核 |
| Python | 3.10.9 |
| Web 服务 | Uvicorn 单进程单 worker |
| 框架 | FastAPI 0.141 + SQLAlchemy 2.0.52 |
| 数据库 | SQLite（压测后启用 WAL） |
| 压测工具 | `backend/tests/loadtest.py`（asyncio + httpx 自研） |

## 二、测试方法

所有压测请求通过 `asyncio.Event` 同步起跑，模拟「100 人同一秒点击」的**惊群**场景，而非平缓加压——这是更严苛也更接近真实高峰的模型。

分两个阶段：

- **阶段 A｜本地接口链路**：登录 → 会话列表 → 新建会话 → 拉取消息 → 知识库统计。零 API 成本，用于测后端并发骨架。
- **阶段 B｜真实 RAG 问答**：登录 → 新建会话 → SSE 流式问答。真实调用 DeepSeek 与硅基流动。

指标口径：端到端耗时、首字延迟（TTFT）、**服务端分段耗时**（检索 / 生成，由 SSE 事件回传）、QPS、错误率、P50/P95/P99。

## 三、发现的问题与修复

压测共暴露 **5 个真实缺陷**，其中 2 个是正确性问题，3 个是并发/性能问题。

### 问题 1｜数据库连接池默认配置过小（致命）

**现象**：100 并发下登录 **31.68% 报 HTTP 500**，P50 延迟卡在 **31.9 秒**这个诡异的固定值，总墙钟 124 秒。

**根因**：SQLAlchemy 默认 `QueuePool` 只有 `pool_size=5 + max_overflow=10 = 15` 条连接上限。100 个并发请求中 85 个在池中排队，等满默认 `pool_timeout=30s` 后抛异常 —— 那「31.9 秒」正是池超时。

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached,
connection timed out, timeout 30.00
```

**修复**：`pool_size=20, max_overflow=40, pool_timeout=30, pool_pre_ping=True, pool_recycle=1800`

### 问题 2｜SQLite 未启用 WAL 模式

默认回滚日志模式下，**写操作会阻塞所有读**。压测期间每个请求都在写消息，直接造成读写互相排队。

**修复**：连接建立时设置 `journal_mode=WAL`（读写不互斥）、`synchronous=NORMAL`（WAL 下安全且更快）、`busy_timeout=15000`（遇写锁等待而非立刻失败）。

### 问题 3｜LLM 缓存从不失效（正确性 Bug）

**现象**：管理员**删除文档后**，用户问同样的问题仍会命中旧缓存，返回的引用片段指向**已被删除的文档**（幽灵引用），且答案基于过时知识库。最长要等 TTL 3600 秒才自愈。

**根因**：`cache.py` 只有 `get`/`set`，**没有失效接口**；`kb.py` 删除文档时只调了 `bm25.invalidate()`，漏了 LLM 缓存。上传文档同理。

**修复**：新增 `cache.clear()`，在上传成功与删除文档时调用。

### 问题 4｜数据库连接被跨网络调用长期持有（架构级）

这是最隐蔽、也是影响最大的问题，且在两个地方重复出现**同一类错误**：**在等待昂贵的非数据库操作时，一直占着数据库连接。**

**4a. 检索链路**
`retriever.py` 中 `bm25_search(db)` 会开启一个 SQLAlchemy 事务并取出连接；之后 `await rerank(...)` 网络调用、以及回到 `chat.py` 的 **LLM 流式生成（数十秒）** 期间，事务始终未结束，**连接一直被占用**。

**4b. 登录链路**
`auth.py` 的 `login` 中 `db.query(User)` 取出连接后，在执行 **bcrypt 校验（实测 254ms）** 的整个过程中一直持有该连接。200 并发登录时，40 个线程各自霸占一条连接。

**证据**（压测期间临时加了 `/debug/pool` 诊断端点，200 并发下每 0.25s 采样一次连接池；取证完成后该端点已移除）：

```
t=7.2s  → checkedout 45, overflow 37
t=40.7s → checkedout 43
t=71.9s → checkedout 51
t=73.1s → checkedout 60   ← 20+40 上限被打满
t=80.8s → 全部释放
```

**有 43~60 条连接被连续占住整整 73 秒**，与登录风暴的持续时间完全吻合。

**修复**：用完立即归还连接，且必须先取出后续需要的字段（避免 ORM 对象过期后再触发查询）。
- `retriever.py`：数据库读完后、进入 `rerank` 前执行 `db.rollback()`
- `auth.py`：取出 `UserOut` 与 `password_hash` 后执行 `db.close()`，再执行 bcrypt

**效果**：连接池峰值占用 **60 → 2**（↓30 倍）；200 并发登录从 **18.5% 失败 + P50 35 秒** 变为 **0% 失败 + P50 7.4 秒**。

### 问题 5｜模型客户端每请求重建（性能）

`get_llm()`、`get_embeddings()` 每次调用都新建客户端，`rerank()` 每次新建 `httpx.AsyncClient`。这些客户端内部都持有 HTTP 连接池，**每次新建都意味着一次全新的 TCP + TLS 握手**——每个问答请求因此多付 3 次握手。

**修复**：`@lru_cache` 复用 LLM / Embedding 客户端，共享一个模块级 `httpx.AsyncClient` 用于重排。

## 五、瓶颈分析结论

1. **瓶颈已从服务端转移到上游 API 配额。** 100 并发冷启动时，服务端检索仅 1.22s、生成 3.77s，其余耗时来自 DeepSeek / 硅基流动的网络往返与排队。这是我们无法优化、但可以通过缓存与限流保护的部分。

2. **「持有连接的时长」比「连接池大小」更关键。** 本例中把连接池从 15 扩到 60 只是缓解；真正解决问题的是把 bcrypt 和 LLM 生成期间的连接持有时间从数百毫秒/数十秒降到毫秒级，峰值占用因此从 60 降到 2。

3. **当前架构无法横向扩展。** 向量索引、BM25 索引、LLM 缓存**全部在进程内存中**，因此只能跑单 worker；一旦开多 worker，各进程的数据会不一致。这是单机演示版的固有限制，也是后续演进的首要方向。

4. **异步端点不受线程池限流保护。** 同步端点（登录、会话）受 anyio 40 线程上限保护，而异步端点（问答）直接并发，压力会原样传导到数据库与上游 API。生产环境需要显式的限流/排队。

## 六、后续优化建议

| 优先级 | 方向 | 说明 |
|---|---|---|
| 高 | 数据库换 PostgreSQL / MySQL | 获得真正的行级并发写与成熟连接池，摆脱 SQLite 单写者限制 |
| 高 | 缓存换 Redis | 当前缓存为进程内存，多 worker 不共享；换 Redis 后可横向扩展 |
| 高 | 增加限流与排队 | 保护上游 API 配额，避免高峰把配额打满导致整体不可用 |
| 中 | 向量库换独立服务（Milvus 等） | 与 BM25 一起从进程内存中解耦，才能多副本部署 |
| 中 | BM25 换 Elasticsearch | 当前 BM25 为纯 Python 实现且**同步阻塞事件循环**，知识库规模变大后会成为瓶颈 |
| — | ~~为 `/debug/pool` 加鉴权或移除~~ | ✅ 已处理：该端点为压测期临时诊断用且无鉴权，取证结束后已从代码中移除 |

## 附：复现方式

```bash
cd backend

# 1. 预注册压测用户（默认 100 个）
python tests/loadtest.py --scenario setup --users 100

# 2. 阶段 A：本地接口 100 并发
python tests/loadtest.py --scenario local --users 100

# 3. 阶段 B：真实 RAG 100 并发冷启动（真实调用大模型，注意配额）
python tests/loadtest.py --scenario rag --users 100 --nonce --timeout 600 --report report.txt

# 4. 阶段 B：100 并发缓存命中（零 API 成本）
python tests/loadtest.py --scenario rag --users 100
```

> `--nonce` 为每个问题附加唯一工单号以强制缓存未命中，用于稳定复现冷启动。
> 压测完成后请清理测试数据（用户名统一为 `loadtest_` 前缀，便于识别与删除）。
